## STAGE 1

- **Objective/users:** Resolve the controlling report deadline in one bounded municipal-law lineage after a later local law replaces an earlier relative-date formula. Consumers are civic compliance calendars and public-law registries; this is not a general legal-opinion engine.
- **Trust problem / GenLayer need:** An earlier law may state a deadline relative to its effective date while a later enacted amendment inserts a calendar date. Official code and legislative-status pages expose the relationship in prose. A single scraper should not decide which expression controls. Validators independently read the same sealed official HTML and agree on identity, enactment, effective date, amended field, and controlling value.
- **Core mechanism:** Register one jurisdiction, base-law ID, amending-law ID, and at most three official source URLs; seal a query day and target field; consensus returns `identity_match`, `amendment_enacted`, `amendment_effective_on_day`, `target_field_match`, `controlling_deadline`, and `evidence_state`. Deterministic logic derives `deadline_resolved`.
- **Actors:** lineage owner, assessor, downstream reader. No payments or private evidence.
- **Evidence/web sources:** legislative clerk, official code publisher, gazette, or municipal legal-notice pages; HTTPS allowlist, URL/hash/retrieval-day binding, bounded text.
- **Concrete public source set, checked 2026-09-21:** [NYC Code Library L.L. 2024/128](https://codelibrary.amlegal.com/codes/newyorkcity/latest/NYCadmin/0-0-0-229581) identifies enactment on 2024-12-21, states in section 26 that Local Law 55 section 5 is amended from `[2 years after effective date of this local law]` to `June 30, 2026`, and states in section 29 that L.L. 128 takes effect one year after enactment. The [NYC Council record for Int. 0436-2024](https://nyc.legistar.com/LegislationDetail.aspx?GUID=62FCF30F-3D9E-4148-B1ED-4469F3985796&ID=6558062&Options=&Search=) independently marks status `Enacted`, enactment date `12/21/2024`, law number `2024/128`, and summarizes the same report-deadline amendment. The exact fixture resolves `controlling_deadline=2026-06-30` for query days on/after 2025-12-21. Counterexample: retaining the bracketed two-years-after-effective formula would produce 2027-12-21 and must be rejected. The Code Library warns that consolidation may lag; disagreement or changed bytes yields `UNRESOLVED`.
- **Validator approach:** leader extracts the closed tuple; validators refetch and independently derive it. Exact-match all consequential fields; explanations are display-only. Source instructions are untrusted data.
- **Consequences/reuse:** `operative_text_ready` may enable a rules engine or freeze it for manual review. Reusable primitive: version-precedence oracle for public law.
- **Closest idea:** Regulatory Edition Applicability Lock (name-only in the collision repository) and Terms of Service Material Change Monitor. **Inherited:** versioned public evidence. **Material difference:** resolves multi-instrument legal precedence on a historical query day rather than detecting semantic change or mapping a profile to a policy. **Difference:** high. **New value:** deterministic time-indexed operative-text view. Not a minor variation because its state key, precedence graph, query, and downstream consequence differ.
- **Risks/assumptions:** no legal advice; only this exact lineage is in MVP; ambiguous identity, amendment, effective-day, or code-publication drift yields `UNRESOLVED`. HTML retrieval is evidenced; current GenVM fetch behavior remains a later build-stage probe.
- **Stage 1 acceptance:** bounded independent evidence, clear consequential tuple, no existing-name collision, material distinction documented, fail-closed behavior, reusable read view.

## STAGE 2

- **Vocabulary/model:** `DeadlineLineage`, `AmendmentRevision`, `EvidenceManifest`, `DeadlineQuery`, `Assessment`. Lifecycle: `DRAFT -> SEALED -> ASSESSED`; assessment may be `RESOLVED`, `NOT_YET_EFFECTIVE`, or `UNRESOLVED`; a changed source set creates an append-only revision.
- **Invariants/storage:** one owner; jurisdiction, base-law, amending-law, and target-field IDs immutable; exactly 2-3 unique HTTPS URLs on sealed origins; bounded strings; unique manifest/query hashes; monotonic revision; prior results immutable. `RESOLVED` requires all decision predicates and an ISO deadline. Store typed scalars, arrays, and mappings only.
- **Public API:** `create_deadline_lineage`, `seal_revision`, `assess_deadline`, `supersede_lineage`, `get_lineage`, `get_assessment`, `is_deadline_resolved`.
- **Authorization/validation:** owner controls draft/seal/supersede; anyone may assess once sealed; canonical day and hashes; reject duplicates, redirects, unknown enums, oversized evidence, and replay with changed payload.
- **Prompt/untrusted boundary:** delimit source text; explicitly ignore commands in evidence; request exact JSON schema; never let narrative explanation set state.
- **Leader/validator/EP:** both independently fetch and extract; validator compares every decision field and rejects malformed/error results. Store accepted tuple only after consensus.
- **Decision vs explanation:** all six fields above are consensus-bound; bounded citations/reason codes may be stored, free-form analysis is not authoritative.
- **Errors/retry/replay/appeal/timeout:** fetch/parser failure => no write or `UNRESOLVED`; idempotent identical replay; corrected evidence requires new revision; appeal is a new query referencing the prior assessment; timeout never changes state.
- **Tests:** direct tests for auth, bounds, transitions, later explicit date controlling, pre-effective query, wrong law/field, stale code bytes, contradiction, hostile text, malformed output, disagreement, replay, and rollback.
